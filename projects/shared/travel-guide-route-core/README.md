# 晨的旅行助手 · 路线排序模块

微信小程序「晨的旅行助手」里负责排路线的部分。给定一批带坐标的景点，算出一条不来回折返的参观顺序，分摊到每一天，并给当天的走法打个顺路分。这个目录把这块逻辑从项目里抽出来单独运行，不依赖小程序、云函数和地图 SDK，`node src/route_demo.js` 一条命令就能看到全部结果。

## 项目信息

这是二组的实验室项目分享，项目全称是旅行攻略生成器（基于大语言模型的个性化行程规划小程序）。负责人陈乾源同时担任组长和代码实现。二组共 7 人，郭子豪和韩玮婷负责项目设计，梳理已有功能、提出优化方案并整理设计说明；郭紫彤和韩易彤负责计划书撰写；王丽艳和孟想负责 PPT 制作与路演。本目录的代码整理、演示和测试由陈乾源完成。所属方向是新工科 · 智慧文旅，当前状态为可运行。

## 功能与创新点

代码分成四个文件。球面距离在 `src/lib/geo.js`，用 haversine 计算，兼容 `{lat,lon}` 和 `{latitude,longitude}` 两种入参。顺序优化在 `src/lib/tsp.js`，先按最近邻排一版，再用 2-opt 把交叉路段拉直。分日排程在 `src/lib/day-plan.js`，每天从住宿地出发，按时段挑最近的景点，市区和远郊分开处理。顺路度评分和负荷核算在 `src/lib/route-score.js`，算当天相邻景点的平均间距，给出分数和一句解释，并检查景点时长有没有超过 12 小时。

排序只用近似解。17 个北京景点从王府井出发，按数据原始顺序是 134.3 km，最近邻排完 109.5 km，再跑 2-opt 到 101.1 km，一共少走 24.7%。没用精确 TSP 或动态规划，景点只有几十个，精确解要么慢，要么要装第三方库，而用户要的是别折返，不是理论最短。

起点固定不动。每天第一站一定从住宿地出发，所以 2-opt 的内层循环从下标 1 开始，不改 `path[0]`。否则会算出「先绕到中间再回来」的顺序，里程好看但没人会这么走。测试第 2 组有断言盯着这条。

分日排程按市区和远郊两个池子取点。直接按最近邻排会出「上午故宫、下午长城、晚上南锣鼓巷」这种安排，总里程不长，但一天里跑两次远郊。所以距城心 25 km 内算市区，两类各挑自己的最优候选，只有早上已经在远郊、或者市区景点快用完了，才允许当天从远郊开始。长城、十三陵这类就自然聚成了同一天的远郊游。

各种偏好都折算成公里数。出行方式、攻略风格、体力、想玩清单，全部换算成公里加减，和距离一起比较，不用另设阈值。想玩清单给 -400 km 的权重，用户自己收藏的点，绕远也要排进去。

评分只用来解释，不反过来改顺序。分数算完就展示，不写回行程，否则用户手动挪一下顺序，刷新又被改回去。评分只统计有真实坐标（`approx === false`）的点，估算坐标连线会得出假里程，宁可不给分。同一片区的点分数会停在 95，因为它们本来就在 5 km 内。只有跨片区硬塞才会掉分，比如把明十三陵塞进市区那天，95 掉到 69，文案里会点名是哪个点拖累的。所以这个分数只在当天展示，不做跨天排名。

## 环境与运行

需要 Node.js 18 以上，开发时用 22.22.2。没有第三方依赖，不用 `npm install`。数据在 `src/data/beijing-spots.json`，每条有 `name / periods / hours / effort / lat / lon / approx`，不需要另外准备。

```bash
node src/route_demo.js     # 看四部分结果
node tests/test_route.js   # 跑断言，全过退出码为 0

# 或者
npm run demo
npm test
```

## 运行结果

顺序优化的结果如下。

| 走法 | 总里程 |
| --- | --- |
| 按数据原始顺序 | 134.3 km |
| 最近邻 | 109.5 km |
| 最近邻 + 2-opt | 101.1 km |

排出来的顺序：

```text
【王府井·出发】 → 天坛公园 → 前门大街 → 国家博物馆 → 天安门广场 → 故宫博物院
→ 景山公园 → 北海公园 → 恭王府 → 什刹海 → 南锣鼓巷 → 雍和宫 → 798艺术区
→ 圆明园 → 颐和园 → 香山公园 → 明十三陵 → 八达岭长城
```

分日排程得到 6 天常规日加 1 天远郊一日游，17 个景点全部排进去，合计约 243.6 km（每天从住宿地单独算）。核心城区那两天是 7.2 和 8.7 km，往外走的几天在 20 km 上下，最远的两处单独成日，没有混进市区。部分输出：

```text

  晚上  什刹海        1.5 h   体力 1   本段 1.6 km

...
D6（常规日 · 动线 44.0 km）
  上午  明十三陵      3.0 h   体力 2   本段 44.0 km  【远郊】
```

| 当天动线 | 分数 | 判定 |

自测输出：`node tests/test_route.js` 的结果是 `全部通过：33 通过 / 0 失败`。断言检查的是行为，包括优化后里程有没有真的变短、景点有没有丢或重复、起点有没有被改、远郊有没有混进市区日、想玩清单有没有排进去、估算坐标有没有被拒绝计分。

## 数据与开源许可

代码随仓库根目录的 [MIT License](../../../LICENSE) 发布。`src/data/beijing-spots.json` 的 17 条坐标取自本项目自建的离线坐标库（项目里的 `SPOT_COORDS`），`approx: false` 表示景点本体坐标，不是城心近似，没有从第三方数据集下载，也没有用需要授权的地理数据。本目录不涉及模型训练和推理，没有模型文件，全部是手写的排序和评分逻辑。代码只用了 Node.js 内置模块 `fs` 和 `path`，没有引入第三方库，也没有从别处拷来的算法实现，算法从本组项目的 `utils/planner.js` 和 `utils/travel.js` 移植过来。

地图底图方面，小程序用微信原生 `map` 组件，网页版用高德地图 JS API，遵循高德开放平台的服务条款。本仓库不含任何高德 Key、云开发环境 ID 或后端凭据，克隆下来不用配置就能跑。三张截图是从我们自己开发的产品里截的，没有第三方素材。想在线看完整产品可以打开网页版 <https://travel-guide-web-15680.app.workbuddy.host/?sharecode=GNIS3D26NE>，链接失效时以本目录的 demo 输出为准。
